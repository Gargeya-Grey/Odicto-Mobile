# Architecture

## Runtime flow

Android IME/overlay -> AudioCaptureService -> direct external provider APIs -> session-checked InputConnection insertion.

- Raw: recorded PCM is sent as WAV directly to Groq Whisper after release.
- AI: Groq transcribes speech, then Gemini or OpenRouter receives the spoken instruction, any explicitly selected text, and the device-saved custom system prompt (or the default when blank).
- Live: PCM streams directly to Gemini Live; provisional words update one native composing range in the original editor. Finalization finishes composition without pasting a second copy. Cursor/content verification prevents subsequent writes after the target changes. Cancel/error retains already typed words.
- Text polish: an explicit IME tap sends only the selected substring, or the whole field when the selection is empty, to OpenRouter with the separate polish model/prompt. Complete-field reads are transient local guards; only the captured target range is replaced after revalidation. Typing alone makes no provider request.

Provider calls run in Kotlin. User API keys are stored in Android Keystore-backed encrypted preferences and used only with the selected provider. There is no local model, PC service, installation-token exchange, or Odicto gateway in the Android voice path. Modes are selected before recording.

React/Capacitor hosts settings and onboarding. Native Kotlin owns recording, provider transport, editor policy, and insertion. The retained Fastify workspace serves the separate web/backend implementation; Android voice does not call it.

## Earlier backend design (not used by Android voice)

The production target is a Node 22 Fastify container on Google Cloud Run, Supabase Pro Postgres, Upstash Redis, and RevenueCat. Cloud Run supplies managed autoscaling, spend caps, integrated observability, and a published runtime SLA. Supabase is the affordable managed Postgres/account layer; database access stays standard and portable because Supabase Pro itself has no contractual uptime SLA.

Postgres is authoritative for installation credentials, idempotent operations, quota, usage, and entitlements. Redis provides short-window installation/IP rate limits only. RevenueCat verifies Play purchases and sends idempotently processed entitlement events.

## Native safety model

`DictationCoordinator` binds recording, processing, and delivery to an operation ID, monotonic editor-session ID, target/connection identity, and selection version. `EditorPolicy` is rechecked before insertion; stale targets are rejected. `DeliveryOutcome` separates `CONFIRMED`, `ACCEPTED_UNVERIFIED`, and `REJECTED_STALE`. The current native targets conservatively map successful Android API calls to accepted-but-unverified, not proof of visible insertion, including Live finalization. Provider completion and history persistence are separate: `VoiceSession` reports Saved only after the Room write succeeds, guards late callbacks by result ID, and keeps failed/unverified results available for explicit Copy rather than expiring them as insertion success. No automatic insertion or provider retry occurs; users should inspect the field before pasting to avoid duplicates.

`KeyboardStatusPresentation` owns only the IME's one-line feedback and monotonic deadlines. It keys voice feedback by operation/result/phase, so meter and history callbacks cannot renew a terminal deadline; newer Polish/Copy notices suppress old voice feedback. Lifecycle changes remove view timers without clearing results or replaying expired messages. Busy feedback has no timeout; terminal feedback defaults to three seconds with the platform accessibility extension. Six fixed toolbar slots and a Polish recovery surface replacing the existing content slot preserve keyboard geometry. The 120-second Polish recovery lifetime and persistent unverified voice recovery remain distinct and unchanged.

These presentation contracts are separate from acceptance evidence: neither a matching installed APK hash nor a registered IME proves stable on-screen geometry or successful insertion. See the [bounded status verification handoff](s24-ultra-testing.md#keyboard-status-fix-bounded-verification-handoff) for observed checks and remaining physical coverage.

The keyboard microphone and the optional overlay call the same recording service/state machine. `DictationCoordinator` routes the finished text to the Odicto IME's `InputConnection` while Odicto is the active keyboard. The published store build registers that IME target and nothing else: it ships no AccessibilityService and no floating overlay, so protected apps such as banking apps have no accessibility capability to flag. The legacy flavor keeps `OdictoAccessibilityService` for inserting into a non-Odicto keyboard's field; that service tracks focus and inserts text only, and it stands down whenever the IME owns the editor.

The Odicto IME is a working keyboard, not a voice strip: letters, shift, numbers, symbols, emoji, a locally retained clipboard panel, and a spacebar that types a space on a tap or moves the cursor horizontally when armed. `SpaceGesture` decides the gesture without Android types, `CursorNavigator` computes the new selection over grapheme clusters, and `KeyboardController` is the single place that writes to the editor. Cursor gestures are refused while a voice request is running or an AI selection is captured, so they cannot invalidate a pending rewrite or a Live composing range. `EditorPolicy` keeps separate answers for manual typing, dictation, emoji, and clipboard: typing works in numeric and phone fields, while everything that reads or writes on the user's behalf stays out of password and no-personalized-learning fields.

`FieldPolishSnapshotReader` verifies complete text against the text before, inside, and after the selection without changing it; partial, styled, oversized, protected, or unreadable fields are refused even for a short selection. `FieldPolishSnapshot` separates complete guard text from the normalized target range and provider payload. `FieldPolishCoordinator` cancels on typing, selection, focus, or voice changes and rechecks session, connection, complete text, selection, and generation before a bounded replacement. A selected operation preserves surrounding text and selects the replacement (including reversed selection direction); whole-field operations map the cursor. Post-commit verification distinguishes applied text from unverified delivery. Unapplied/unverified completed results have bounded in-memory Copy/dismiss recovery for 120 seconds, with no automatic retry or persistent Polish history.

Clipboard capture, storage, and rendering are separate: `ClipboardCapture` gates a lifecycle-owned listener; `ClipboardRepository` serializes exact-text mutations and legacy migration in a dedicated versioned DataStore; `ClipboardPanel` renders saved state and exposes capture, pin/unpin, and deletion controls. For eligibility, retention, migration loss, and disclosure requirements, read [Privacy and security](privacy-and-security.md#local-clipboard-and-editor-reads). For precise hit bounds, cursor/hold thresholds, and width-driven split layout, read [Keyboard feel settings](android-development.md#keyboard-feel-settings). Compact chrome is IME-only; the floating overlay's size, placement, layout, and gestures remain unchanged.

AI captures a request-scoped selection snapshot at recording start, including the cursor when nothing is selected. Before committing, native code checks the original editor, selection range, selected text, and observed selection changes. Changed or unreadable selections fall back to local history/copy without moving the cursor or restoring a stale selection. Android 12+ uses `getSurroundingText(0, 0, 0)` for selection-only snapshots; older Android uses IME selection callbacks with `getSelectedText`. Unsupported or oversized snapshots fail closed. See [Android InputConnection](https://developer.android.com/reference/android/view/inputmethod/InputConnection). Raw and Live do not capture selection context.

The legacy accessibility target re-resolves the focused `AccessibilityNodeInfo` on every read and insert, applies the same `EditorPolicy` predicate (`inputType` + `isPassword`), and splices text at the reported selection via `ACTION_SET_TEXT`, with `ACTION_PASTE` as the fallback for editors that expose no text. Live composing is IME-only; selecting Live with the accessibility target falls back with the existing message.

Choosing AI mode pre-selects the whole field so the rewrite target is the entire text; a range the user already picked is left untouched. Tapping a cursor afterwards collapses the selection, and the answer is inserted at that point instead.

## Manual input continuity

These are implementation contracts; replay and physical evidence is recorded separately in [S24 Ultra testing](s24-ultra-testing.md). `KeyboardController` serializes manual writes on the IME thread. Ordinary characters commit immediately relative to the editor, without frame-spanning batches, per-letter selection queries, or speculative absolute cursor repair. Compound mutations such as guarded uppercase replacement use operation-scoped batches closed in `finally`, outside reads, waits, and frame callbacks.

`EditorSessionState` separates observed host selection/context from predicted local state, records composing bounds, and binds work to a connection and reset epoch. Its ordered edit ledger is bounded to 32 entries (forward typing can coalesce); overflow marks ambiguity rather than confirming delivery. `EditorTail` holds a bounded 96-UTF-16-unit suffix plus completeness, not a single expected cursor. Missing context or an exhausted partial suffix is not confirmed document start, and unknown selection remains unknown rather than becoming zero. Service callbacks forward old/new directed selection and composing bounds. Local ledger positions are bookkeeping, not Android acknowledgment IDs: compatible coalesced evidence can retire a unique prefix without rewinding prediction, while matching an old cursor alone cannot prove ownership. Android supplies neither tagged callbacks nor an atomic read/check/delete transaction.

`DeleteRepeatCoordinator` has `Idle`, `Running`, `AwaitingEvidence`, and `AtBoundary` phases. The dispatch window permits at most two unconfirmed character operations or one bounded word operation, blocks pending typing/word work and ambiguity, and stops granting credit once the oldest pending work exceeds 240ms. Context is acquired at the start or refreshed at context/credit boundaries, not queried on every trusted repeat. Refresh attempts are spaced by at least 80ms unless fresh progress resets the gate. Word deletion uses bounded trustworthy context; a partial word reaching the cached edge falls back to a character step. The view schedules one monotonic absolute deadline at a time and skips missed ticks instead of catching up in a deletion burst.

Transient stale/missing evidence retains pointer ownership while destructive dispatch waits; compatible evidence permits the same hold to resume without lift/repress. Unknown absolute metadata can fall back to readable bounded suffix evidence, but repeated/ambiguous suffixes cannot establish unique progress. Opaque or protected editors can exhaust the small evidence allowance; manual taps and the no-read policy remain, not a promise of universally uninterrupted holds. Null metadata responses remain retryable rather than being permanently classified as unsupported; otherwise a transient host failure would disable recovery. Release/cancellation, incompatible external edits, failed deletes, or replacement end the old hold; already submitted remote work cannot be recalled. Dictation, Live, Polish, paste, and cursor movement are manual-state handoff/invalidation boundaries. Start/restart, hide/unbind, finish, and view disposal cancel obsolete session work.

Pointer and haptic behavior is specified in [Keyboard feel settings](android-development.md#keyboard-feel-settings); diagnostic endpoints and the isolated host are described under [Current trace — debug-only, content-free](android-development.md#current-trace--debug-only-content-free). Actual measurements belong in [S24 Ultra testing](s24-ultra-testing.md), not inferred from these contracts.

## Deferred

Billing/accounts, production Redis integration, Play Integrity, RevenueCat webhooks, and iOS are gated after physical Android POC acceptance. iOS cannot provide an Android-style overlay or microphone-enabled custom keyboard.
